# R6 支付中心冻结设计

## 1. 阶段边界

R6 只建设支付中心，不进入退款、售后、配送、佣金、提现、结算、发票、对账单下载等后续能力。

旧的用户端公开超时关闭订单入口 `/api/v2/app/orders/expired/close` 必须移除。`CloseExpiredOrders` 仅保留为内部服务能力，由调度任务、内部 Job 或测试控制入口触发，不再暴露给 App JWT API。

## 2. 核心原则

- 前端支付回调不代表真实支付成功。
- 只有支付渠道签名验签通过的异步通知，或服务端主动查询支付渠道后确认的结果，才能推动订单进入 `PAID`。
- 支付金额只允许来自 `orders.payable_amount`，客户端不得提交金额、支付状态、三方交易号。
- 支付通知必须幂等。
- 支付成功与库存扣减必须在同一个业务事务内完成。
- Mock 支付只允许开发和测试环境使用，生产环境禁止启用。

## 3. 新增数据表

### payments

保存订单支付单。订单与支付单是一对多关系，允许同一订单因重试、关闭、失败等场景产生多笔支付单，但最终只能由一笔支付单推动订单成功支付。

核心字段：`payment_no`、`order_id`、`order_no`、`user_id`、`provider`、`channel`、`status`、`amount`、`currency`、`provider_trade_no`、`provider_prepay_id`、`client_request_id`、`expire_at`、`paid_at`、`closed_at`、`failed_at`。

状态枚举：`CREATED`、`PENDING`、`SUCCESS`、`CLOSED`、`FAILED`。

### payment_events

保存支付渠道通知、查询同步事件与处理结果，用于审计、排查和幂等。

核心字段：`payment_id`、`payment_no`、`provider`、`event_type`、`provider_event_id`、`provider_trade_no`、`payload_hash`、`processed`、`process_result`、`error_message`、`processed_at`。

## 4. 支付 Provider 边界

统一接口：

- `CreatePayment`
- `QueryPayment`
- `ClosePayment`
- `VerifyAndParseNotification`

R6 首先实现：

- `WechatPayProvider`：微信支付边界，真实商户参数缺失时返回配置错误，不伪造成功。
- `MockPaymentProvider`：仅开发/测试环境使用，用于自动化与本地调试。

## 5. 支付成功事务

`HandlePaymentSuccess` 必须：

1. 锁定支付单。
2. 锁定订单。
3. 校验支付状态。
4. 校验三方金额、支付单金额、订单应付金额一致。
5. 更新支付单为 `SUCCESS`。
6. 更新订单为 `PAID`。
7. 按订单明细执行库存 `DEDUCT`。
8. 写入库存流水。
9. 写入支付事件处理结果。

库存扣减幂等约束：

- `reference_type = ORDER`
- `reference_id = order_no`
- `type = DEDUCT`
- 唯一约束：`sku_id + reference_type + reference_id + type`

## 6. R6 API

### 用户端

- `POST /api/v2/app/orders/:id/payments`
- `GET /api/v2/app/orders/:id/payment-status`

### 支付渠道通知

- `POST /api/v2/payments/wechat/notify`
- `POST /api/v2/payments/mock/notify`

通知入口不使用 JWT，安全性来自支付渠道签名验签。

### 后台只读

- `GET /api/v2/admin/payments`
- `GET /api/v2/admin/payments/:id`

后台 R6 不允许手工置成功。

## 7. R6 不做内容

- 退款
- 售后
- 配送履约
- 分销佣金
- 余额提现
- 财务结算
- 人工改支付成功
- 生产 Mock 支付
